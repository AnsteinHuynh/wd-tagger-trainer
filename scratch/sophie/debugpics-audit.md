# debugpics audit: 459e2a02 and 4ec33484

Read-only audit. I read `wdtag/train.py` (`dump_debug_pictures` at lines 235-253, `dump_stream_debug` at lines 256-269, the dump trigger in `StepHelper.step` at lines 331-360, the manifest reload at lines 318-323) and `wdtag/stream.py` (`_order` at lines 188-192, `_iter_tar` at lines 91-116, `_produce` at lines 216-273). I read both runs' `config.json`, each run's `debugpics/manifest.json`, the checkpoint config stored inside `ckpt_step001000.pt`, the per-tar count table in `runs/_manifests/manifest_train.json`, the tar headers of `00023.tar`, and a sample of the dumped PNGs. I did not modify anything under `runs\`, did not launch training, did not allocate CUDA, and deleted nothing.

The order rule I recomputed is exactly the documented one: sorted tar names, then `random.Random(seed * 1000003 + pass_index)` shuffling that list, then file order inside each tar, pairing each image member with the following json member of the same stem. For seed 1337 and pass_index 0 the RNG seed is 1337004011; the train directory holds 213 tars and the shuffled order begins `00023.tar`, `00083.tar`, `00172.tar`. `00023.tar` contains 25000 complete image/json pairs according to `runs/_manifests/manifest_train.json`, and its first pairs in header order are `1744892`, `709195`, `833858`, `8700385`, `1286200`, each as `stem.webp` then `stem.json`.

Run 459e2a02: config seed 1337, stream true, mode squash, 512px, batch 64, grad_accum 6, 100 PNGs, manifest 100 entries. Its checkpoint `ckpt_step001000.pt` stores the same seed 1337, batch 64 and grad_accum 6, which matters because `config.json`'s mtime is 2026-10-24T11:05:22, later than the pictures. Every one of the 100 manifest entries records tar `00023.tar`, and the key sequence is byte-for-byte the first 100 pair keys of `00023.tar` in file order: exact ordered match, no renames, no reordering, no entries from any other tar, 100 unique keys, first key 1744892 and last key 7557846. The manifest's file names are all `key-00023-squash.png` and all 100 exist on disk with no orphan PNG and no missing file.

Run 4ec33484: config seed 1337, stream true, mode squash, image_size 384, batch 48, no grad_accum, 100 PNGs, manifest 100 entries, all tar `00023.tar`. Its key and file sequence is identical to 459e2a02's, entry for entry. Its checkpoint `ckpt_step001000.pt` also stores seed 1337 and batch 48. So the same seed produced the same first 100 samples across a 512px run and a 384px run, which is what the streamer's determinism claim predicts, and the 384 run's dump spans three separate dump calls, so the continuity holds across call boundaries too.

Image spot-checks, all pixel-exact against a fresh decode of the named tar member with `Image.convert("RGB")` then `resize((SIZE, SIZE), Image.BILINEAR)`, comparing the full array at maxdiff 0. In 459e2a02, entry 0 `1744892-00023-squash.png` is 512x512 from a 900x600 source, entry 63 `2546385-00023-squash.png` is 512x512 from a 640x1139 source, entry 64 `5605845-00023-squash.png` is 512x512 from a 640x640 source, and entry 99 `7557846-00023-squash.png` is 512x512 from a 1280x640 source. In 4ec33484, entries 0, 64 and 99 are keys 1744892, 5605845 and 7557846 at 384x384, the same keys as the 512px entries 0, 64 and 99, and they also match their tar members exactly. All 100 PNGs in 459e2a02 are 512x512 and all 100 in 4ec33484 are 384x384, with 100 distinct pixel hashes in each run, so nothing is duplicated. The 900x600 and 640x1139 sources arriving as squares is the squash contract visible in the pixels, not a misdescription. For contrast I checked pad-mode run 7ff9ee38: its `5314184-00092-pad.png` is 512x512 and carries the padding bars, and its file name says `pad`, which is the index-mode naming path.

The one run where the correspondence fails is 4a13a120, stream true, seed 1337, batch 48, no accumulation, mode squash, with a `.PAUSE` file present and its oldest checkpoint `ckpt_step050519.pt`. Its manifest's first sample is `4581770-00166-squash.png`, which is pair index 24912 of `00166.tar`; `00166.tar` is at shuffled position 96 and the tars before it hold 2400000 samples, so that first picture is global sample 2424912, exactly 50519 x 48. Its entries 0-87 are `00166.tar` pairs 24912-24999 and entries 88-99 are `00047.tar` pairs 0-11, the next tar in the shuffled order, both slices matching the manifest key for key. That is the pass's samples 2424912 onward, not samples 0-99, and the manifest records no start offset or pass index, so nothing in the directory says the "first 100" are a resumed window.

Two further runs never reached 100: `4ffefeb8` has 48 entries and `73be0d5b` has 48 entries, both starting correctly at `1744892-00023-squash.png`, each stopping after one optimiser step (batch 48 with no accumulation, and batch 24 with grad_accum 2). Those are incomplete rather than misordered, but they show the dump count is a run-length artefact a reader must check.

Two defects are latent rather than observed. `dump_stream_debug` hardcodes the `-squash` suffix in the file name even though the index path uses `self.cfg.mode`, and the streaming decoder always resizes to `SIZE` with no pad branch, so a streaming run configured `pad` would silently dump squashed pictures labelled `squash`; no such run exists among the 49 streaming runs with debugpics, all of which are `squash`. Streaming manifests also store `dataset_id: null` where index-mode manifests store the integer id, so the stream dump loses the label-space id. The append concern does not hold: `manifest.json` is reopened with mode `w` on every dump and rewritten from the in-memory list (`train.py` lines 268-269), the loaded count caps further dumps at 100 (`train.py` lines 318-323 and 348-360), and both audited runs show exactly 100 unique entries with manifest mtime equal to the last PNG mtime.

Verdict: for runs 459e2a02 and 4ec33484 the seed-to-picture correspondence holds exactly and the dumped pixels are faithful descriptions of what the trainer saw, but the contract breaks silently for a resumed streaming run, as 4a13a120 shows with its first picture at global sample 2424912 (step 50519 x 48) while still presenting itself as the pass's first 100.
