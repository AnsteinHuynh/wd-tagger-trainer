# Compilation and kernels

Production trainer: no `torch.compile` at all. The only dynamo reference in `src/` is the disable decorator (`oft.py:263-269`). → Your 359→290 ms compile win already beats this production loop
The good pattern (`train_rotasim.py:371-384`): bind `fwd = model.forward_pair` once, then if enabled `torch._dynamo.config.suppress_errors = True; fwd = torch.compile(...)`. (a) forward only — "All checkpointing / state_dict / named_parameters access stays on the uncompiled module, so saved keys never gain a `_orig_mod.` prefix"; (b) `suppress_errors` lets inductor fall back to eager for CPU-side graphs (`376-380`: `InvalidCxxCompiler`, no MSVC on the box); (c) bound once, not re-wrapped per step. → High: the shape that cannot trip a recompile limit, because optimizer and mutable cache never enter a graph
`@torch._dynamo.disable(recursive=True)` on the cache getter (`oft.py:263-269`): "Inlining this branch into dynamo would either bake the stale path in or force a recompile every step; a disabled region keeps the graph guards stable." → High: a Python-side mutable tensor looks like a new input every step
No SDPA/flash pinning, no `attn_implementation`, no cudnn.benchmark, no CUDA graphs, no Triton kernels, no `foreach` (all absent); HF default sdpa. → Gap; at 1024 tokens the bottleneck is GEMMs, not attention, but untested here
Blocked einsum for the OFT apply (`oft.py:254-260`): reshape to `(..., n_blocks, block_size)`, `einsum("...bk,bkc->...bc")`, `repeat` only when `block_share` → cost linear in block_size² per block instead of a dense per-layer matrix
